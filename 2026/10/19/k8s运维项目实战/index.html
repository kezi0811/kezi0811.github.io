开启 ingress-nginx Controller 的监控指标（metrics）暴露功能，让 Prometheus 等监控工具能采集 ingress-nginx 的运行数据。

开启状态：当值为 true 时，ingress-nginx Controller 会在 10254 端口上暴露 /metrics 端点（比如 http://:10254/metrics），这个端点会输出 Prometheus 格式的监控指标（如请求数、响应时间、错误率、连接数等）。

关闭状态：若设为 false，10254 端口不会暴露 /metrics 端点，监控工具无法采集 ingress-nginx 的运行数据。

helm更新ingress-nginx配置

Prometheus 的数据指标是通过一个公开的 HTTP(S) 数据接口获取到的，我们不需要单独安装监控的 agent，只需要暴露一个 metrics 接口，Prometheus 就会定期去拉取数据；对于一些普通的 HTTP 服务，我们完全可以直接重用这个服务，添加一个 /metrics 接口暴露给 Prometheus

05 NetworkPolicy

NetworkPolicy可以类比为防火墙，只是这个防火墙作用对象是Pod，源和目的是 Pod、namespace、ipblock这三类资源，方向有ingress和egress两种。

在默认情况下，pod的出方向、入方向都是允许所有。

在定义ingree和egress规则时，pod区分来源或目的使用以下三种标识：

1、pod，限制本pod不能被其他pod访问、或者限制本pod不能访问其他pod，用label来匹配pod

2、namespace，限制本pod与目标namespace的互访，也是用label匹配

3、ipblock，限制本pod与目标网段的互访，使用ipblock，cidr区块

fsCroup与supplementalGroups

  1. fsGroup（文件系统组）

核心定义：fsGroup 是专门针对 Pod 中挂载卷（volume） 的组权限配置，它会强制将 Pod 内所有挂载卷的文件 / 目录的属组（GID） 设置为该值，同时让容器进程的有效组包含这个 GID。

核心作用：解决「容器运行用户（runAsUser）」与「卷文件属组」不一致导致的读写权限问题，尤其是多容器共享卷的场景。

通俗举例：

你之前的配置中 fsGroup: 555，无论容器用 runAsUser: 1111 还是 2222 运行，/volume 目录的属组都会被设为 555，且容器进程会自动获得 555 组的权限，因此两个不同用户的容器都能读写该目录。

关键特性：

只对 挂载卷 生效，不影响容器根文件系统的文件权限；

Kubelet 会自动修改卷的权限（添加 sgid 位），确保卷内新建文件的属组也是 fsGroup；

优先级高于卷本身的默认属组。

  1. supplementalGroups（补充组）

核心定义：supplementalGroups 是给 Pod 内所有容器进程添加的附属组列表，相当于 Linux 中 usermod -aG 组ID 用户名 的效果，让进程同时属于多个组。

核心作用：扩展容器进程的组权限，使其能访问那些属于这些补充组的文件 / 资源（不一定是挂载卷）。

通俗举例：

你配置的 supplementalGroups: [666,777]，意味着 Pod 内的容器进程除了自身的主组、fsGroup 外，还会属于 666、777 这两个组。如果宿主机 / 卷中有文件的属组是 666，且权限为 rw-r—–，容器进程就能读取该文件。

关键特性：

作用于整个 Pod 内的所有进程，不限于挂载卷；

不会主动修改文件的属组，只是让进程「加入」这些组，从而获得对应权限；

可以配置多个组（数组形式）。

pod-with-shared-volume-fsgroup.yaml

进入容器，容器运行用户属于555,666，777三个组。挂载目录下创建的新文件，属于555组

Pod Qos

根据Limit和Request的比例将Pod分为三个等级：

1、Guaranteed(保证级)级别：

最稳定、最后被杀死

2、Burstable(突发级)：

当节点资源不足时，仅当Pod的实际资源使用量超过requests时，才可能被驱逐；

驱逐优先级：使用量越接近limits，requests占比越低的pod，越容易被杀死。

3、BestEffort(尽力级) –最不稳定、最先被杀死

当资源不足时，杀死顺序：

BestEffort > Burstable > Guaranteed

当一个pod内有多容器，会以等级最小的容器等级作为pod的等级

下图四个Pod被杀死的顺序是：

pod3 - pod2 - pod4 - pod1

LimitRange

用于规范Pod或容器的资源限制

LimitRange是对单个pod或容器资源的限制

创建一个LimitRange

example-limit-range.yaml

重点解释Container部分的参数

  • type: Container # 规则作用对象：Pod内的单个容器（每个容器都要遵守该规则）

max: # 单个容器的「资源上限（limits）」：不能超过以下值

cpu: “500m” # 单个容器的CPU limits最大500毫核（0.5核）

memory: 512Mi # 单个容器的内存limits最大512Mi

min: # 单个容器的「资源下限（requests）」：不能低于以下值

cpu: “100m” # 单个容器的CPU requests最小100毫核（0.1核）

memory: 64Mi # 单个容器的内存requests最小64Mi

defaultRequest: # 「默认资源请求（requests）」：容器未手动配置requests时，自动填充该值

cpu: “200m” # 未配置requests.cpu的容器，默认填充200m

memory: 128Mi # 未配置requests.memory的容器，默认填充128Mi

default: # 「默认资源上限（limits）」：容器未手动配置limits时，自动填充该值

cpu: “300m” # 未配置limits.cpu的容器，默认填充300m

memory: 200Mi # 未配置limits.memory的容器，默认填充200Mi

maxLimitRequestRatio: # 「资源上限/请求的最大比例」：限制limits不能比requests大太多

cpu: “2” # 单个容器的 limits.cpu / requests.cpu ≤ 2（比如requests.cpu=200m，limits.cpu最大400m）

memory: “4” # 单个容器的 limits.memory / requests.memory ≤ 4（比如requests.memory=128Mi，limits.memory最大512Mi）
